# 1  文档概述

## 1.1  目的

本文档把一个「一人多平台内容运营」的真实工作流，转写为可开发的软件需求：明确系统要解决的问题、功能边界、模块划分、数据与接口约定、部署形态、验收标准与风险约束，作为研发、测试、运维的共同基线。

## 1.2  范围

覆盖范围：发布工程生成与校验、多平台内容填写与（部分）自动提交、数据采集、转化归因、日历与档案、复盘与周报、通知与看板同步、远程访问与鉴权、移动端小组件、体检与人工兜底、安装与自启。

不在本期范围：云端 SaaS 化、多租户账号与权限体系、团队协作、全自动无人值守发布（详见第 12 章）。

## 1.3  术语与缩略语

| 术语 | 释义 |
|---|---|
| 期（Issue） | 一期内容，对应一套成片 + 封面 + 各平台文案 + 定时，是系统的最小业务单元。 |
| 发布工程 | 一期内容在磁盘上的目录，含成片、字幕、发布素材.md、多比例封面。 |
| 发布素材.md | 固定章节结构的 Markdown，人可读、可版本管理，是各平台文案的单一事实来源。 |
| publish.json | 由 发布素材.md 生成并经校验的结构化发布包，供分发引擎消费。 |
| 播种 | 把一期内容填入各平台上传页的动作（多平台发布）。 |
| 长势 | 播放/互动与粉丝数据采集模块。 |
| 收成 | 转化归因模块，统计注册、会员、订单、收入来源渠道与期数。 |
| 粮仓 | 档案模块，沉淀每期封面、文案快照、平台链接、过程日志。 |
| CDP | Chrome DevTools Protocol，通过远程调试端口驱动浏览器。 |
| 专用 Chrome | 独立用户目录与调试端口（默认 9333）的 Chrome 实例，仅存平台登录态，不存密码。 |
| 半自动 | 系统完成填写与核对，最终「发布」按钮由人工点击。 |
| daemon | 常驻守护进程，负责调度、提醒、采集、复盘生成。 |

# 2  项目背景与目标

## 2.1  业务背景

一条视频剪完后，需要分发到 B站、抖音、小红书、视频号、YouTube、X、Instagram。每个平台的文案口径、封面比例、标题长度、标签规则都不同；发布完成后还需要回答「哪一期起来了、哪个平台在涨粉、哪个平台真正带来了付费」这三个问题。

现有工具的普遍短板：只做「一键分发」，不做后半程的数据采集、归因与复盘；或走向另一个极端，做全自动群发，账号风控风险高、数据不在自己手里。

## 2.2  产品定位

> 给「一个人做内容、要发六七个平台」的创作者使用的开源本地工作台 —— 把多平台发布、数据采集、转化归因、复盘通知串成一条本地自动化流水线。

## 2.3  建设目标

| 编号 | 目标 | 衡量方式（建议） |
|---|---|---|
| G1 | 消灭多平台重复填写、重复上传的机械劳动 | 单期 7 平台从手工 60+ 分钟降至 ≤15 分钟人工确认时间 |
| G2 | 发布全链路可追踪：发布 → 取链接 → 采数据 → 复盘 → 归因 → 通知闭环 | 任一期可查到各平台链接、每日数据、第 1/3/7 天复盘卡片 |
| G3 | 数据自主可控，不依赖第三方 SaaS | 全部数据落本地 SQLite；无外部上报 |
| G4 | 对平台账号友好，可持续 | 不存密码、不绕风控、国内平台人工终审 |
| G5 | 低成本可维护、可二次开发 | 零第三方 npm 依赖；平台改版仅需更新插件 |

## 2.4  设计原则（三条硬边界）

| 原则 | 具体要求 |
|---|---|
| 不存任何平台密码 | 通过驱动本机已登录的「专用 Chrome」的登录态操作，经由 CDP 控制，系统本身不接触账号口令。 |
| 国内四家只填不发 | B站、抖音、小红书、视频号只负责填写与核对，最后一步由人点击，降低平台风控风险。 |
| 数据只在本地 | SQLite 落盘本地；网页需口令访问；系统本身不上报任何数据。 |

# 3  目标用户与使用场景

## 3.1  用户画像

| 角色 | 特征 | 核心诉求 |
|---|---|---|
| 个人创作者（主） | 一人运营 5–7 个平台，日更或周更 | 少花时间在重复发布上，看清哪个平台值得投入 |
| AI 内容创作者 | 已用 Claude Code / Codex 写文案与脚本 | 让 AI 直接产出发布工程，系统负责校验与分发 |
| 小团队（1–3 人） | 有剪辑 + 运营分工，无专职开发 | 一台常开 Mac 承担自动化，数据留本地 |

## 3.2  典型场景

| 场景 | 现状痛点 | 系统行为 |
|---|---|---|
| S1 多平台分发 | 同一条视频在 7 个后台上传 7 次，手动改标题、标签、封面比例 | 读发布工程，按批次在专用 Chrome 中填好 7 个平台；国内 4 家停下等人工点发布 |
| S2 发布后盯数据 | 每天手动翻后台看播放、涨粉 | 每日上午自动采各期各平台播放/互动与粉丝；新一期头三天每 6 小时采一次 |
| S3 判断内容好坏 | 凭感觉，无法同口径对比 | 发布后第 1/3/7 天自动出复盘卡片，含同龄对比（第 N 天 vs 第 N 天） |
| S4 渠道收益归因 | 只知道总收入，不知哪期哪个平台带来付费 | 通过 utm_campaign=<主题>-<序号> 归因注册/会员/订单/收入，输出播放→注册→会员→收入漏斗 |
| S5 排期与回看 | 发布计划散落在备忘录 | 日历展示上周到未来两周：已发布 / 已定时 / 等你点 / 计划中 |
| S6 异常与漏发 | 定时被平台改掉、上传框关掉但其实已排期 | 定时被篡改检测、防重校验、守护进程每 20 分钟提醒待人工发布 |

# 4  总体设计

## 4.1  系统组成

系统由三块协作构成一个「本地中控台」：

| 部件 | 职责 | 形态与位置 |
|---|---|---|
| 发布 Skill | 让 AI 助手（Claude Code / Codex）看片、写各平台文案、生成发布工程并校验 | 仓库内 skills/maitian-publish/SKILL.md |
| 麦田发布助手 | Chrome 插件，各平台适配器：打开上传页、传视频与封面、填文案、设定时 | Chrome 应用商店（自动更新），不随主仓发版 |
| 麦田（主程序） | 分发计划、调度、防重、等待人工发布、取链接、采数据、大屏、飞书通知 | 本仓库，Node 进程 + SQLite |

## 4.2  端到端链路

```
成片
└─ AI skill 写「发布素材.md」
└─ 生成 publish.json 并校验
└─ hub plan 进分发计划
└─ hub run 分批填入各平台（专用 Chrome）
├─ 海外/自有站点：自动提交
└─ 国内平台：人工点「发布 / 定时发布」
└─ 到点自动取链接回填
└─ 每天采播放/粉丝数据
└─ 网页大屏 + 飞书卡片 + 复盘/周报
```

## 4.3  分层架构（逻辑视图）

| 层 | 组成 | 关键约束 |
|---|---|---|
| 接入层 | Web 大屏/日历/复盘/转化页（:8787）、演示模式（:8788）、iOS Scriptable 小组件、飞书卡片 | 单一口令鉴权，接口无口令一律 401 |
| 应用层 | hub CLI（plan/run/status/sync/mark/submit/adopt/metrics…）、daemon 调度、review/weekly 生成 | 全部 ESM，单文件单职责 |
| 领域层 | 期与任务状态机、防重规则、批次策略、校验规则、归因计算 | 规则与平台适配解耦 |
| 适配层 | Chrome 插件适配器（lib/publish.js、lib/cdp.js）+ chrome-shim 在 Node 侧模拟扩展 API | 平台改版只更新插件 |
| 驱动层 | CDP（专用 Chrome :9333）、child_process 拉起 Chrome/cloudflared/ffmpeg | 不使用 element.click()，用真实鼠标点击 |
| 存储层 | node:sqlite 落盘 data/hub.db；config.json；Markdown 作为输入格式 | 零第三方依赖 |

## 4.4  运行形态

一台常开的 Mac（官方唯一保证平台）作为自动化主机，跑 Node 常驻进程 + 一个专用 Chrome。

Windows 为社区适配脚本（开机自启未适配，可用任务计划程序替代）；Linux 无官方路径。

不适合无图形界面的云服务器：系统本质是「本机自动化」，依赖登录态与真实浏览器。

# 5  功能需求

优先级定义：P0 = 闭环必需（缺失则主流程断裂）；P1 = 显著影响体验与效率；P2 = 增强/可选配置。

每项需求包含编号、优先级、需求描述与验收要点，可直接转换为开发任务与测试用例。

## 5.1  M1 发布工程与素材校验

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-01 | P0 | 支持以固定章节结构的「发布素材.md」作为唯一文案输入源，人可读、可进 git 版本管理。 | 给定素材 md，可解析出各平台标题/正文/标签/定时等字段；章节缺失时报错并定位到行。 |
| FR-02 | P0 | 由素材 md 生成结构化 publish.json（make-publish），作为分发引擎的唯一输入。 | 生成结果字段完整、可被 run 直接消费；重复生成幂等。 |
| FR-03 | P0 | 发布工程校验（validate）：字数限制、禁用词、封面比例、faststart 编码、命名规范等。 | 不按规范（如成片未命名为 成片.mp4、缺 faststart、封面比例不符）时被拦截并给出可读原因。 |
| FR-04 | P0 | 发布工程目录规范：<rootPath>/<系列>/<期>/ 下放 成片.mp4、可选 字幕.srt、发布素材.md、封面三种比例。 | 封面支持 cover-3x4.png / cover-4x3.png / cover-16x9.jpg，按平台自动选用对应比例。 |
| FR-05 | P1 | AI 侧 Skill 提供「看片 → 写发布素材 → 确认封面 → 建发布工程 → 生成并校验 publish.json」流程。 | 在 Claude Code / Codex 中说「整理发布」可触发；产出物直接可交给 hub plan。 |

## 5.2  M2 分发计划与调度

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-06 | P0 | hub plan：登记发布工程进分发计划；不带目录时扫描 rootPath 自动发现新工程。 | 扫描可增量发现，已登记的不重复登记。 |
| FR-07 | P0 | hub run：按计划在专用 Chrome 中分批填好各平台上传页，支持 --only 指定平台、--force 强制重跑、--now 立即执行。 | 参数生效；单平台失败不影响其他平台；失败原因入库可查。 |
| FR-08 | P0 | 批次策略 batches：一次上传平台过多会抢带宽导致超时，需可配置批次（建议国内两两一批）。 | 配置生效，批次间串行、批次内按策略并发。 |
| FR-09 | P0 | hub status [id] [--logs]：查看期/任务状态与过程日志。 | 可看到每个平台当前状态、最近一次动作时间、错误摘要。 |
| FR-10 | P0 | daemon 常驻进程：执行调度、提醒、采集、复盘生成；由 launchd 托管开机自启。 | 进程异常退出后可被自动拉起；重启后计划与状态不丢失。 |
| FR-11 | P1 | 等待人工发布的平台，守护进程每 20 分钟提醒一次直至完成。 | 提醒通过飞书卡片下发，状态变更后停止提醒。 |

## 5.3  M3  平台适配层（Chrome 插件 + CDP）

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-12 | P0 | 专用 Chrome 以远程调试端口（默认 9333）和独立用户目录启动，Node 侧通过 WebSocket 直连标签页（CDP）。 | 不读取、不存储平台密码；登录态仅存在于 chrome-profile/ 目录。 |
| FR-13 | P0 | 主程序直接加载插件目录下的 lib/publish.js、lib/cdp.js 作为平台适配引擎，用 chrome-shim.mjs 在 Node 中模拟 chrome.tabs / chrome.debugger。 | 主仓库无需打包插件即可复用同一套适配逻辑。 |
| FR-14 | P0 | 使用真实鼠标点击（cdp.click）而非 element.click()，降低被识别为自动化的概率。 | 点击事件具备可信坐标与事件序列。 |
| FR-15 | P1 | 平台改版只需更新插件，所有用户自动生效，主仓库不用跟随发版。 | 适配器版本独立于主程序版本；插件更新后无需重装主程序。 |
| FR-16 | P0 | 支持平台范围：B站、抖音、小红书、视频号、YouTube、X、Instagram，外加可选的「自有站点」。 | 每个平台具备独立的适配器与状态标记。 |

## 5.4  M4  提交策略、防重与状态机

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-17 | P0 | 自动提交 vs 人工发布分流：X、YouTube、Instagram、自有站点在回读文案与定时一致后自动提交；B站、抖音、小红书、视频号填好即停，等人工点击。 | 每平台提交模式可配置（auto / manual）。 |
| FR-18 | P0 | 防重机制（本地）：库中已到位的平台不再重复执行。 | 重复 run 同一期时跳过已完成平台并说明跳过原因。 |
| FR-19 | P0 | 防重机制（平台侧）：X 定时列表、YouTube Studio、Instagram 主页、站点后台已有同名内容的不再上传。 | 同名判定需回读平台已有内容，避免重复投稿。 |
| FR-20 | P1 | 定时被平台改掉时检测并告警（如视频号定时被平台修改）。 | 发现计划时间与平台实际时间不一致时发飞书告警并记录差异。 |
| FR-21 | P0 | 取链接回填：hub sync 在到点后自动获取各平台发布链接，回填「已发布」状态。 | 一期可查到 7 个平台的可点击链接。 |
| FR-22 | P1 | 人工兜底命令：hub mark 手动改状态、hub submit 单独补提交、hub adopt 登记已发过的期。 | 三条命令均能在不移除数据的前提下修正状态。 |

## 5.5  M5  数据采集（长势）

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-23 | P0 | 每天上午采一次各期各平台播放/互动数据与各平台粉丝数，长期留存。 | 采集结果落库为快照，可按时序查询；单平台采集失败不影响其他平台。 |
| FR-24 | P0 | 新一期发布后头三天按每 6 小时一次的高频采集。 | 高频窗口到期后自动回落到每日一次。 |
| FR-25 | P1 | 采集完成后自动汇总生成日报并推送飞书。 | 日报含全平台播放、粉丝、今日涨粉等核心指标。 |
| FR-26 | P1 | hub metrics [id] / hub followers 支持按需手动触发采集。 | 手动与定时采集共用同一采集器与幂等策略。 |

## 5.6  M6  转化归因（收成，可选）

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|
| FR-27 | P2 | 接上自有站点后，采集注册、会员、订单、收入数据，并归因到渠道与期数。 | 需站点按 src/site.mjs 顶部注释改造，暴露两个只读接口（课程/仪表盘）。 |
| FR-28 | P2 | 归因口径：utm_campaign=<主题>-<序号>，由系统在生成发布链接时写入。 | 同一期在不同平台可区分；无 utm 的流量归入「未知」。 |
| FR-29 | P2 | 转化页输出「播放 → 注册 → 会员 → 收入」漏斗。 | 各层数值可与采集快照对上，漏斗转化率计算正确。 |

## 5.7  M7  日历与 M8 粮仓（档案）

| 编号 | 优先级 | 需求描述 | 验收要点 |
|---|---|---|---|

## 10.2  三种安装方式

### 方式一：一行安装（推荐，macOS）

`bash -c "$(curl -fsSL https://raw.githubusercontent.com/CzzzzzzJ/mdldm-maitian/main/scripts/install.sh)"`

脚本行为：① 校验 git 与 Node 版本（≥ 22.5）；② 克隆/更新仓库到 ~/maitian/mdldm-maitian（可用 MAITIAN_HOME 改目录）；③ 把 skills/maitian-publish 软链到 ~/.claude/skills/maitian-publish（已存在则不动）；④ 执行 node src/init.mjs 安装向导：检查环境 → 生成 config.json → 装开机自启 → 打开各平台登录页。

向导结束后访问：http://localhost:8787/?key=<web.key>（浏览器会记住口令）。

### 方式二：手动安装

```
git clone https://github.com/CzzzzzzJ/mdldm-maitian.git
cd mdldm-maitian
node src/demo.mjs        # ① 先用假数据看效果：http://localhost:8788/?key=demo
node src/init.mjs        # ② 安装向导：检查环境、生成 config.json、装开机自启
node src/hub.mjs doctor  # ③ 登录完各平台后体检（不上传、不填写）
```

若不走向导：

```
cp config.example.json config.json   # 按注释填写 rootPath、feishuWebhook、web.key 等
bash scripts/install-launchd.sh      # 安装开机自启（可加 --tunnel 同时装 Cloudflare 隧道）
```

### 方式三：Windows（社区适配）

`powershell -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/CzzzzzzJ/mdldm-maitian/main/scripts/install-windows.ps1 | ..."`

安装到 %USERPROFILE%\maitian\，同样接 skill、打开向导。

安装目录含 4 个双击启动器：1-demo.bat、2-login.bat、3-doctor.bat、4-start.bat。

需要 Windows 10/11 + Node ≥ 22.5 + Chrome；缺 Git/Node 时用 winget 自动补装。

开机自启暂未适配，可用任务计划程序指向 4-start.bat。

## 10.3  启动后最小闭环

```
node src/hub.mjs login          # 打开专用 Chrome 和各平台页面供登录
node src/hub.mjs plan [工程目录] # 登记进分发计划（不带目录=扫描 rootPath）
node src/hub.mjs run <工程目录> [--only x,xhs] [--force] [--now]

node src/hub.mjs followers      # 采粉丝
node src/hub.mjs review <id> [天数] [--notify]
node src/hub.mjs weekly [--notify]
node src/hub.mjs daemon         # 常驻（launchd 装的就是它）
```

## 10.5  运维注意事项

Chrome 升级、标签页卡死需人工处理；卡死标签页可 curl 127.0.0.1:9333/json/close/<id> 关闭。

平台改版可能导致填写失效，需更新插件（主程序无需发版）。

SQLite 落在 data/，无内置备份/导入导出机制，数据备份与迁移需自行负责（见 12.3 建议）。

Mac 休眠/断网会中断发布与采集，建议关闭休眠或使用电源保持常开。

# 11  验收标准

## 11.1  分层验收（对应上手成本分级）

| 层级 | 范围 | 验收判据 |

| L1 只看数据（约 30 分钟） | 安装、演示模式、大屏与日历 | demo 模式假数据大屏可正常浏览；配置 rootPath 后能读到已有期 |
| L2 做分发（再加约 1 小时） | 登录、plan、run、sync | 一期 7 平台可完成填写；国内 4 家停在待人工；人工点发布后 sync 取到链接 |
| L3 接转化（视站点） | 站点接口、utm 归因、漏斗 | 转化页可展示播放 → 注册 → 会员 → 收入，且与采集快照一致 |

# 12  范围外事项与后续规划

## 12.1  明确不做（本期）

| 不做项 | 原因 |
|---|---|
| 云端 SaaS 形态、多租户 | 设计为本地单用户工作台，数据只在本地 |
| 账号体系、权限模型、团队协作 | 只有一个网页口令，无角色/权限设计 |
| 国内平台全自动发布 | 有意为之的「半自动」克制设计，规避平台风控 |
| Linux 官方支持 | 无官方路径；本质是本机图形环境自动化 |
| 内置数据备份/迁移 | SQLite 落在 data/，备份需自理 |

## 12.2  已知短板（原文自述）

强绑定 macOS；Windows 为社区适配且开机自启未适配；Linux 无官方路径。

需要一台常开的 Mac + 专用 Chrome；Mac 休眠/断网直接影响发布与采集。

依赖平台页面结构，天然易碎；Chrome 升级、标签页卡死需人工处理。

半自动而非全自动，追求「排完就睡」的用户会有落差。

存在平台合规/风控风险，账号后果需自行承担。

单用户设计，不适合团队协作。

工程化偏轻：无单测目录、无 CI、无正式版本化 Release。

前置约定较多：目录规范、成片命名、双比例封面、faststart、素材 md 固定章节。

数据备份与迁移需自理；转化功能非开箱即用（需改造自有站点）。

## 12.3  建议的后续增强（整理者建议，非原文）

| R-02 | 内置 data/ 备份与导入导出（导出 zip / 定时快照） | 解决备份迁移自理的问题 |

## A.2  实战总结的坑位（原文 README 摘录，需内化为校验规则）

| 坑位 | 规则要求 |
|---|---|
| 视频号定时会被平台改 | run 后必须回读校验，发现差异告警 |

| Chrome 标签页卡死 | curl 127.0.0.1:9333/json/close/<id> 强制关闭后重试 |
